# iMedics HIS Update Handoff

## Nursing observations, care tasks, handovers and the pharmacy medication-order workflow

This workstream closes the nursing and pharmacy gap from the delivery plan. Four additive tables (`nursing_observation`, `nursing_task`, `nursing_handover`, `medication_order`; migration `20261101000000_his_nursing_pharmacy`) back three new API areas and two new screens, all following the existing HIS patterns: facility-scoped queries, exact case-number + date-of-birth patient identification, `assertPatientLinked` patient linkage, permission gates and audit entries on every write.

**Nursing** (`/lab/nursing`, `/api/facility/his/nursing/**`): observations come from a fixed type/unit registry (`src/lib/his/observation-types.ts`, client-safe pure data). Each entry stores the clinical timestamp (defaulting to now, future timestamps rejected), the value, the registry-fixed unit, the author and an optional note. Validation is format-only — no clinical thresholds, scores or automatic flags are invented, per the delivery plan. Care tasks run a guarded lifecycle DUE → IN_PROGRESS → COMPLETED with DEFERRED/ESCALATED side exits and reopening; completing stamps the time. Shift handovers record a summary and attach the patient's open tasks (validated to belong to this facility and patient). New permissions: `RECORD_NURSING` (NURSE), `ORDER_MEDICATIONS` (DOCTOR, SURGEON, DEPARTMENT_HEAD), `REVIEW_MEDICATIONS` (PHARMACIST); OWNER retains all.

**Pharmacy** (`/lab/pharmacy`, `/api/facility/his/medication-orders/**`): orders carry medication name, strength, dose, route, frequency, duration, notes and the prescriber, and move DRAFT → SUBMITTED → REVIEWED → DISPENSED → COMPLETED, cancellable at live stages. Permission gates run before transition validation so unauthorized callers cannot learn workflow state: submitting requires `ORDER_MEDICATIONS`, reviewing and dispensing require `REVIEW_MEDICATIONS`, and only the prescriber can cancel. The worklist attaches each patient's recorded allergies (from the medical history) for reviewer visibility — the system performs no interaction checking and suggests no dosing; it is workflow tooling, not an e-prescribing or dispensing-hardware integration, and MAR-style administration recording remains out of scope.

Verification: 945 tests passing across 116 files (29 new: 10 domain-rule tests plus route tests for observations, tasks, task transitions, handover attachment, order creation, worklist allergy attachment, permission gates and lifecycle denials), ESLint clean, TypeScript clean, optimized production build successful, and the additive migration applying cleanly to the main and acceptance databases. ## Resumable multipart uploads, storage quotas and session cleanup

The next workstream closes the remaining diagnostic-media gap: true resumable multipart transfer, facility storage quotas and abandoned-session cleanup. Files at or above `HIS_MULTIPART_THRESHOLD_BYTES` (default 64 MB) open a `MedicalMediaUploadSession` (additive migration `20261031230000_his_multipart_sessions`) and upload through presigned part URLs; part URLs are issued in batches on demand, and a retried file skips the parts the storage service already holds. Completion is verified server-side from the storage service's own part list — contiguous part numbers, full-size non-final parts, exact declared total — never from client-supplied ETags, then runs the same signature/checksum/scan/registration tail as the single-PUT path (shared in `src/lib/his/media-record.ts`). The presign route refuses uploads that would exceed the facility quota (`HIS_MEDIA_QUOTA_BYTES`, default 20 GB) with 403; a failed session-row insert aborts the storage multipart upload, and a failed final verification abandons the session and aborts storage. `GET /api/cron/media-upload-sessions` (CRON_SECRET-guarded, idempotent) aborts expired sessions hourly. New tests cover part sizing, quota admission/refusal, session state validation, part-list verification and the three routes; browser retry now resumes instead of restarting the file.

## Previous update changes (e40d346)

- **Patient-linked attachments and images:** template fields now select actual diagnostic-media UUIDs instead of displaying a placeholder. Draft save, submission and finalization verify hospital, patient, deletion state, infection state, MIME compatibility and sensitivity. Required references must be present. Lab, imaging and endoscopy catalogue defaults include supporting-file fields; persisted hospital versions are unchanged. PDF/print exports identify the reference, explicitly state the file is not embedded, and do not disclose storage keys or signed URLs. File access and patient release remain separate.
- **Surgical catalogue completion:** four missing Group E entries are appended: Anesthesia consent, Surgical consent, Procedure-specific informed consent, and Biopsy request and consent. Appending preserves the source codes of existing entries. They use the consent structure with locked disclosure fields, patient/representative and consenting-clinician signatories. Wording and emergency/incapacity handling still require local clinical and legal validation.
- **Protected-record access:** worklists, API searches and patient portfolios exclude other authors' specially protected documents unless the staff member has review permission. Media lists exclude specially protected files for non-reviewers. Workflow actions and package export now enforce the same document-read restriction as direct reads. Media mutation also enforces protected-file access.
- **Template integrity:** both source and hospital-specific locks survive editing. Mandatory fields cannot gain hiding conditions, lose bounds/columns or broaden allowed choices. Mandatory signature alternatives cannot be broadened; locked independent review cannot be disabled. Duplicate section identifiers and inverted numeric bounds are rejected.
- **Concurrency:** template lifecycle actions and draft saves use guarded parent/version writes inside one transaction. A stale save cannot rewrite a submitted/published version. Document autosave is serialized with explicit save/submit, and completing an old save no longer clears the dirty state of newer edits.
- **Diagnostic verification and release:** upload confirmation requires review permission to mark a result VERIFIED/AMENDED. Reviewers can verify an existing preliminary result from the media page. Release supports VERIFIED and AMENDED reports; revocation is available. Returning a report to UNREPORTED/PRELIMINARY automatically revokes patient release. Media updates use hospital-scoped optimistic writes to reject a concurrent delete or status change.
- **Upload safety:** a configured malware scanner must explicitly return CLEAN or INFECTED. Pending, unknown, malformed and unsuccessful results fail closed; requests time out after 30 seconds. No scanner still means NOT_SCANNED, never CLEAN. Failed checksum/scanning or metadata persistence triggers deletion of the unregistered final object. Infected objects cannot be viewed or released. Storage deletion itself can fail and requires operational monitoring.
- **Validation:** numeric fields reject booleans, date-only fields reject calendar-invalid dates, required text cannot be whitespace-only, and tables enforce column counts and reject wholly empty required rows.
- **Dependency maintenance:** compatible transitive security updates are recorded in package-lock.json. No framework major upgrade or schema migration was introduced.

## Deployment and configuration

Deploy the existing project through its normal GitHub/Vercel integration. The earlier e40d346 patch needed no new migration; the continued implementation above adds two migrations and optional isolated-acceptance configuration documented in HIS_ACCEPTANCE.md. The navigation follow-up adds no migration. Do not run database commands against production without reviewing the current schema and backups.

The existing environment must supply Clerk configuration, Postgres URLs and private S3-compatible storage. Configure bucket CORS for presigned uploads and enforce private access, encryption, lifecycle/retention policy and operational logging. The existing optional MALWARE_SCAN_URL integration must return JSON `{"result":"CLEAN"}` or `{"result":"INFECTED"}`; MALWARE_SCAN_TOKEN supplies its configured authentication. When scanning is a hospital requirement, enabling and validating that service is a release gate.

Adopt the newly appended consent templates through the hospital template library. Existing versions do not silently acquire new fields. To add a supporting-file field to an existing published hospital template, create a new version, edit, submit, independently approve if required, and publish. Existing signed records continue pointing to their original version.

## Specification boundaries

The repository contains broad A–P catalogue scaffolds, encounters/admissions, coverage, settings, portfolio, audit and operational analytics. All 18 specialty defaults now have distinct structured fields; other catalogue forms still include generic structures, and every template requires clinical review. Full nursing/medication workflows, comprehensive observation/escalation protocols, cross-hospital grants, caregiver delegation, scheduling integrations and complete department policy remain unfinished.

Tenant authorization remains application-level and storage-key-level, with additional PostgreSQL write-time link/identity guards in this continued update. This is not RLS: unrestricted SQL read access still bypasses application authorization. Tenant-read isolation and private-bucket policies require a reviewed infrastructure rollout; database-enforced tenant isolation is not complete.

HL7/FHIR file acceptance is not an operational interoperability gateway; DICOM upload is not PACS/RIS integration. Device interfaces, accredited/qualified e-signatures, certificate revocation/timestamps, durable queue delivery guarantees, disaster recovery, retention enforcement, independent security review and jurisdiction-specific consent/legal sign-off remain deployment work. Critical clinical mutations now persist audit rows transactionally; supplementary metadata/read logging remains best-effort in places. This is not a complete tamper-evident clinical audit ledger.

Attachment references are not automatically embedded into exported PDFs or records packages, are not automatically released to patients, and are not a medical-image viewer. The selector shows the latest 200 eligible patient media records. Archived/unavailable references remain visible as identifiers and cannot be newly submitted/finalized until corrected.
